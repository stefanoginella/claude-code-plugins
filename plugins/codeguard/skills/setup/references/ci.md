# CI

Default provider is **GitHub Actions**. If the repo already runs a
different CI (GitLab CI, CircleCI, etc.), evaluate what's there and extend
it instead of introducing a second provider — ask if there's a preference
before assuming.

## Security hardening — apply these regardless of what jobs you add

- **Pin every third-party action to a full commit SHA, not a tag.** A tag
  is mutable; a SHA is the only immutable reference. Pin with a trailing
  comment naming the version for readability:
  ```yaml
  - uses: actions/checkout@<full-commit-sha-of-the-latest-release> # vX.Y.Z
  ```
  Look up the SHA of the *current* release at setup time (the tag's
  commit on the action's repo) — don't copy a pinned example from docs or
  memory, which is how a stale or wrong pin spreads.
- **Least-privilege `permissions`.** Set a restrictive default at the
  workflow level and grant write scopes only on the specific job that
  needs them:
  ```yaml
  permissions: {}   # or read-all, depending on the job

  jobs:
    lint:
      permissions:
        contents: read
  ```
- **No long-lived cloud credentials in secrets** where the provider
  supports OIDC — request a short-lived token via `id-token: write`
  instead of a static access key sitting in repo secrets indefinitely.
- **Gate changes to workflow files themselves** via `CODEOWNERS` on
  `.github/workflows/` — a workflow file with write-scoped permissions is
  itself an attack surface if anyone can edit it unreviewed.
- Validate every workflow file with **`actionlint`** before considering
  setup done — it catches YAML/shellcheck/expression errors that would
  otherwise only surface on the next push.

## Job skeleton

Adapt job names/commands to the detected stack's tools from
`references/git-hooks.md`. A representative shape:

```yaml
# generated by codeguard v<plugin-version> — delete this line to take ownership
name: ci
on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  quality:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@<pinned-sha> # vN
      - name: Set up toolchain
        uses: <stack-appropriate setup action>@<pinned-sha> # vN
      - name: Install dependencies (frozen lockfile)
        run: <package manager install --frozen-lockfile equivalent>
      - name: Lint
        run: <lint command>
      - name: Type-check
        run: <type-check command>
      - name: Test with coverage
        run: <test command>
      - name: Patch coverage gate
        run: <diff-coverage command>

  security:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      security-events: write   # only if uploading SARIF (e.g. to code scanning)
    steps:
      - uses: actions/checkout@<pinned-sha> # vN
      - name: Secret scan
        run: <gitleaks/trufflehog invocation>
      - name: SAST
        run: <semgrep invocation>
      - name: Dependency audit
        run: <stack audit command>
      - name: Slopsquatting / new-dependency check
        run: <slopcheck/guarddog invocation, scoped to newly added deps>

  mutation:
    # only where the stack's mutation-testing tool is CI-mature
    # (StrykerJS, Infection) — run on a schedule or main-branch merge,
    # not on every PR, since it's slow
    if: github.event_name == 'push' || github.event.schedule
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@<pinned-sha> # vN
      - name: Mutation testing
        run: <mutation tool invocation>
```

Split into fewer or more jobs based on what got approved — don't ship an
empty `mutation` job if mutation testing wasn't in the plan, and don't
merge `quality`/`security` into one job just to shorten the file if the
repo would benefit from separate required-status-checks.

## Frontend addition

If tier 6 (frontend) safeguards were approved, add a job (or steps) for:
- Accessibility lint (already covered at commit-time by
  `eslint-plugin-jsx-a11y` if that's in the hook config — CI re-runs it
  full-repo rather than staged-only).
- Bundle-size / Lighthouse CI budget check, non-blocking initially if the
  repo has no existing budget baseline (a hard-fail on day one with no
  baseline just gets bypassed).

## Adapting to another CI provider

The same jobs translate directly — the concepts (frozen-lockfile install,
lint/type/test, patch coverage, secret scan, SAST, dependency audit,
scheduled mutation testing) aren't GitHub-specific. What changes:
- **GitLab CI**: `.gitlab-ci.yml` stages instead of jobs; GitLab's own
  secret detection and dependency scanning templates can substitute for a
  hand-rolled security job if the repo is on GitLab Ultimate/has them
  enabled.
- **CircleCI**: orbs can replace some manual `uses:` steps; pin orb
  versions the same way as GitHub Actions SHAs.
- Action-pinning-by-SHA is a GitHub Actions-specific practice; the
  equivalent elsewhere is pinning any third-party CI plugin/orb to an
  immutable version rather than a floating tag.
